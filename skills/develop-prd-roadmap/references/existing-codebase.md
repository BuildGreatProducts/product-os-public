# Existing-codebase mode

The repo already has a product. Instead of scoping an MVP from scratch, this mode writes the **target** `docs/PRD.md`, audits today's code against it, takes keep-or-remove decisions with the member, and writes `docs/ROADMAP.md` as a **gap roadmap** — the same format as a new-build roadmap, executed by `develop-build` the same way.

Coming off a prompt-to-app platform (Lovable, Bolt, v0, Base44, Replit Agent)? `develop-migrate` runs first; this mode is the code-quality pass once the app lives in the member's own repo.

## Resuming

If `docs/ROADMAP.md` holds a `## Decisions (draft)` table, an earlier session was interrupted mid-review: confirm the baseline (step 1) exists, re-run the audit (step 3) briefly, and continue from the first difference without a decision.

## 1. Protect the working code

Before anything changes, make sure the member can always get back to the version that works:

1. If `git status --porcelain` shows uncommitted changes, ask the member to commit them first so the baseline captures the working version.
2. Get today's date with `date +%Y-%m-%d`, then branch and tag the starting point: `git switch -c refactor/<YYYY-MM-DD>` and `git tag pre-refactor-<YYYY-MM-DD>`.
3. Tell the member in one line how to get back: `git switch <original-branch>`, or `git reset --hard pre-refactor-<YYYY-MM-DD>` to throw the work away.

## 2. The target PRD

- **`docs/PRD.md` exists and the member confirms it still describes where the product is going** → use it as the target.
- **Otherwise, write one.** The app already answers most of the new-build interview's questions, so skip the full scoping interview:
  1. Read `docs/DEFINE.md` and `docs/DESIGN.md` in full. Missing → run the fast-track producer first (`define-from-code`, `design-design-system-from-code`).
  2. Apply the shape (SKILL.md step 2) — the shape file's Develop route and the PRD variant in `PRD-GENERATION.md` § Shape variants.
  3. Explore the codebase: structure, stack, data model, screens or commands, auth and payment integrations — what the product *is* today.
  4. Interview briefly, one question at a time, drawing on `PRD-GENERATION.md` and `TECH-STACK-OPTIONS.md`: the core loop; what the product must do that today's doesn't; what today's does that should go; the target stack (confirm, or change a layer with a reason).
  5. Write `docs/PRD.md` — the **target state**, in the standard PRD shape and chunks (SKILL.md step 4), opening with the note `> Existing-codebase PRD — the target state, generated by develop-prd-roadmap from DEFINE.md, DESIGN.md, the existing codebase, and the member's decisions.` Spec what exists and stays, what changes, and what's added; skip MVP scoping that doesn't apply.

## 3. Audit the codebase against the PRD

Read the PRD and `docs/DESIGN.md` in full, then explore the repository: structure, dependencies, data model, API or tool surface, screens, and auth and payment integrations. If an earlier `docs/ROADMAP.md` has unchecked tasks, treat them as candidate Missing items. Build a complete list of differences:

- **Missing** — required by the PRD, absent from the code (features, screens, entities, endpoints or tools, states, requirements).
- **Divergent** — in both, implemented differently (stack mismatches, schema differences, other auth or payment providers, a structure that doesn't match the PRD's repository layout, styling that ignores `docs/DESIGN.md` tokens).
- **Extra** — in the code, absent from the PRD (features, dependencies, dead code, abandoned experiments).

For each: the evidence (file paths), the PRD section it relates to, and a one-line impact assessment.

## 4. Decide each difference, one at a time

Never one giant wall. For each difference: what was found, what the PRD says, a recommendation (keep / remove / refactor / defer), and the cost of each option; then the member decides. Group trivially related items where it helps, but every **Extra** needs an explicit keep-or-remove decision and every **Divergent** needs a decision on which side wins — the code or the PRD. If the member keeps something the PRD doesn't cover, note that the PRD needs updating.

**Record each decision as it's made**, so an interrupted session loses nothing: write `docs/ROADMAP.md` with the line `> Draft — existing-codebase review in progress; not yet executable.` and a `## Decisions (draft)` table (difference · classification · decision · PRD update needed?), appending one row per decision. An earlier roadmap is replaced — it's in git history from the baseline commit. These decisions define the roadmap's scope.

## 5. Write the gap roadmap

Once every difference is decided, apply any PRD updates the member agreed to, show the phase outline — titles, goals, rough task counts — and get approval. Then overwrite `docs/ROADMAP.md`, replacing the draft, in the format of `ROADMAP-GENERATION.md` with these differences:

- **Header:** the standard `# Product Roadmap — {productName}`, generated-by note, `**Status:** 0/{total} tasks complete`, and `**Current Phase:**` lines, plus this mode line directly under the title (develop-build reads it):
  `> **Mode:** existing-codebase — a gap roadmap from the current code to docs/PRD.md. Baseline: tag pre-refactor-<YYYY-MM-DD> on branch refactor/<YYYY-MM-DD>.`
- **Refactor Philosophy** (in place of Build Philosophy): the app stays runnable after every phase; removals before rebuilds; one concern per task; existing tests keep passing, and a deliberate behaviour change updates its tests in the same task; build straight through on the refactor branch — review and commit at each phase boundary, no pull request required.
- **Phases** sized to the actual work — typically cleanup and removals → foundation and stack alignment → missing features and parity → polish and verification (plus the eval tasks when Develop Step 1b is scheduled). Each has a descriptive title, a one-sentence Goal, and Reference sections pointing at exact `docs/PRD.md` and `docs/DESIGN.md` headings.
- **Tasks** in the canonical three-line format, IDs sequential across all phases. Every task traces to a decision or PRD requirement, is sized to one agent session (15–45 minutes), and ends its Notes with `Verify:`.
- **Agent Session Guide** as in the guide.
- **Footer — `## Decisions`:** what was kept, removed, and deferred; any PRD updates made; the baseline tag.

## Verify before delivering

- [ ] The baseline branch and tag exist, and the member knows how to get back.
- [ ] Every Extra item has a keep-or-remove decision and every Divergent item says which side wins; no draft table or draft line is left behind.
- [ ] The header carries the `**Mode:** existing-codebase` line; the status line total matches the task count.
- [ ] Every task traces to a decision or PRD requirement, uses the three-line format, and ends with `Verify:`.
- [ ] Removals come before rebuilds, and every phase leaves the app runnable.

Finish by summarizing in conversation — phase count, task total, anything deferred — and point the member at `develop-build`.
